## 반증된 가설
- **"#6 기준(long task 감소)으로 판정할 수 있다"**: 샘플 PDF 기준선은 long task 0건, 하트비트
  p95 6ms. 샘플은 래스터화가 가벼워 병렬화가 드러날 수 없었다. 무거운 PDF로 바꿨다.
- **"첫 타일이 늦은 것은 open()이 모든 워커를 기다려서"**: 조기 반환으로 바꿨지만 1458 →
  1347ms로 조금만 줄었다. 타임라인상 네 워커는 2ms 안에 다 열렸고, 공백은 rAF 지연
  (~895ms)이었다. 조기 반환은 느린 워커를 기다리지 않는다는 설계 이유로 남겼고, 코드
  주석의 잘못된 인과("~1.46s")를 고쳤다.
- **"LoAF 1초는 메인 스레드 작업"**: blockingDuration 0, 스크립트 귀속 없음. 프레임 생성
  자체가 늦었다(창 프레임 제한).

## 검증하지 못한 것
- 첫 타일 시간과 처리량(업로드 수)은 이 창의 rAF 제한에 섞여 판정하지 않았다. 화면에
  실제로 보이는 창에서 다시 재야 한다.
- 메모리: 워커 4개 × (문서 1.8MB + PDFium 힙)의 실제 사용량은 재지 않았다.
- 실제 워커 충돌(WASM trap)은 가짜 워커로만 검증했다.
