## 측정값이 세는 것
- 프레임 수 = `GPUQueue.submit` 호출 수. 앱의 `console.info` 프레임 로그는 프레임
  1~3과 매 60프레임에만 찍히므로 프레임 수가 아니다.
- 모든 카운터는 **브라우저 WebGPU API 호출 수**이고 앱 자체 카운터가 아니다.
- `createBuffer` 160은 "버퍼가 커진 횟수"다. 버퍼는 단조 증가하므로 타일 수가
  안정되면 멈춘다. 프레임마다 1개씩 만드는 것과 다르다.
- 두 구간의 프레임 수가 275 vs 269로 다르다. 같은 조작을 수동으로 재현한 것이라
  정확히 같지 않다. 그래서 절대값이 아니라 **프레임당 비율**로 판정했다.
- `canvasSetSameValue`는 캔버스 크기에 **같은 값을 다시 넣은** 횟수다. 두 구간 모두
  프레임당 정확히 2회(width, height)이고 `canvasResize`는 0이다.

## 반증된 가설
코드 리뷰 때 "매 프레임 캔버스를 리셋하므로 백버퍼가 재할당된다"(F3)를 다음
작업 후보로 꼽았다. 계측 결과 `canvasResize: 0`, `configure: 0`으로 **값이 바뀌는
대입은 한 번도 없었다**. 추정했던 재할당 비용은 측정되지 않았고, 같은 구간에서
훨씬 큰 비용은 버퍼 churn이었다(프레임당 127개 객체). 작업 순서를 바꿔 이쪽을
먼저 처리했다. F3은 issue #5로 남기고 측정 결과를 그 본문에 적었다.

또 하나: "텍스처는 재사용되니 괜찮다"고 보았으나, 재사용되는 것은 텍스처
**객체**뿐이고 그것을 가리키는 **view**는 매 프레임 새로 만들고 있었다
(`createView` 35,096 vs `createTexture` 261).

## 검증하지 못한 것
- 프레임 타임 / long task 시간은 측정하지 않았다. 이 수정이 체감 성능을
  얼마나 바꾸는지는 이 리포트가 말하지 않는다. 객체 생성 수만 말한다.
- Playwright 게이트는 여전히 WebGPU 경로를 실행하지 않는다(issue #7).
  배포 e2e 통과는 2D fallback 무회귀만 뜻한다.
