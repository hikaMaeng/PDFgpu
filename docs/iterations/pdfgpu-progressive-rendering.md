## 상세 설계

1. 앱 로컬 PDF 경로는 순방향, 역방향, 고해상도 A, 고해상도 B를 연다. 첫 슬롯에서 매니페스트를 받고 화면 미리보기를 즉시 시작한다. 나머지는 준비 완료 이벤트로 합류한다. 슬롯당 하나의 렌더를 발행하며 엔진 내부 가용 여부는 현재 문서가 열려 있고 응답을 기다리는 메시지가 없는 슬롯으로 정의한다. 준비·유휴·실패 변화가 뷰어를 깨운다. 시작 또는 문서 열기에 실패한 슬롯을 제외하고 3개는 저·저·고, 2개는 저·고, 1개는 공용으로 축소한다. 준비 중인 슬롯은 실패한 것으로 취급하지 않는다. 기존 `poolSize` 기본값과 직접 래스터 호출 및 캡처 API를 보존한다.
2. 화면 갱신 시 현재 활성 페이지와 실제 보이는 페이지, viewport 및 DPI를 계산한다. 캐시된 96 DPI 이미지를 합성하고 누락된 활성·가시 프리뷰를 정지 대기 없이 저해상도 빈 슬롯에 한 건씩 보낸다. 동일 래스터 키에 두 작업을 보내지 않는다. 스크롤뿐 아니라 페이지 점프, 확대·축소, 보기 모드 및 레이아웃 변경이 최신 화면 상태를 교체한다.
3. 화면 전환은 고해상도 타일의 후속 발행을 즉시 중지한다. 새 화면이 200ms 안정되고 페이지 프리뷰가 준비된 뒤, 빈 고해상도 워커 하나를 현재 화면에 배정한다. 프리뷰 실패가 확정된 페이지도 고해상도 렌더를 허용한다. 타일 한 건을 마칠 때마다 같은 워커가 다음 타일을 가져간다. 이전 워커가 동기 PDFium 호출 한 건을 끝내는 동안 다른 워커가 새 화면을 맡을 수 있다. 둘 다 바쁘면 실제 응답 순으로 배정한다. 뷰어 스케줄러는 시그널로 물리 슬롯을 조기 해제하는 대신 세대로 결과를 판별한다. 현재 화면에서 완성되어 캐시에 들어간 타일은 위치와 DPI가 일치하는 경우 재사용한다.
4. 스크롤이나 페이지 이동이 시작되면 새 프리캐시 작업 발행을 보류한다. 마지막 이동 후 500ms에 활성 페이지가 달라졌으면 커서를 양방향으로 재설정한다. 같은 페이지에서 스크롤이 멈추면 기존 위치에서 계속한다. DPI 변경만으로 프리뷰 탐색이 초기화되지 않는다. 방향마다 한 건을 완료할 때 다음 페이지를 고르고, 캐시 적중은 건너뛴다. 늦은 프리뷰는 같은 문서이며 현재 화면에 필요하거나 프리뷰 예산에 들어갈 때 저장한다. 문서가 바뀌면 비트맵을 해제한다.
5. 타이머는 뷰어가 공유하는 최신 viewport와 캐시를 기준으로 필요한 시점에만 깨우는 단발 타이머를 쓴다. 이동과 렌더 완료 이벤트도 같은 스케줄러를 깨운다. 평소 워커는 열린 상태에서 한 건씩 `postMessage`를 받는다. 백그라운드 폴링은 필요 없다. 워커 내부 큐에 발행할 작업을 미리 쌓지 않는다. 일반 공급자는 보고된 동시성 안에서 활성 화면을 우선하며, 원격 또는 메인 스레드 폴백의 프리캐시는 기존 ±2 이내로 제한한다.
6. 총 192MiB의 기존 예산 안에서 프리뷰 64MiB, 타일 128MiB를 사용한다. 프리캐시에는 96 DPI에서의 메타데이터 예상 크기와 완성 비트맵 크기를 각각 확인한다. 현재 보이는 프리뷰와 해당 기준점에서 후보보다 가까운 프리뷰는 축출 후보에서 제외한다. 예산에 막힌 방향은 기준점이나 캐시 상태가 바뀔 때만 재평가하고 문서 끝에서는 멈춘다. 화면에 필수인 래스터에는 기존의 보호 키 동작을 적용한다. 같은 목표 세대 안의 렌더 실패를 반복 예약하지 않는다.
7. 문서 전환과 dispose는 타이머와 뷰를 무효화하고 늦은 비트맵을 해제한다. 연속 `open`은 최신 문서 식별자를 검사한다. 더 오래된 `open`은 새 문서의 공용 워커에 `close`를 발행하지 않는다. 이전 `load`의 실패나 진행률 콜백도 현재 문서 상태를 덮어쓰지 않는다.

## 구현 및 검증 순서

1. 리뷰 두 회에서 호출 경로, 워커 물리 점유, 화면 세대, 원격 공급자, 메모리와 타일 위치를 우선 반증한다. 소스 사실과 검토 결과를 대조해 설계를 수정한다.
2. 고정 역할을 사용하는 워커 배정과 준비 완료 알림을 구현한다. 기존 직접 래스터 호출, 캡처, 폴백 동작과 늦은 응답 처리를 검증한다.
3. 뷰어를 최신 상태 기반 스케줄러로 전환한다. 캐시 읽기·쓰기와 합성, 렌더 진행률은 기존 소유자에 둔다. 외부에게 이미 공개된 뷰어 옵션·상태·프로바이더 동작을 확인한다.
4. DOM과 분리한 실제 스케줄러에 시간·가용 슬롯·캐시를 주입해 최초 화면, 3→8 점프, 양방향 확장, 캐시 적중, 200/500ms 분리, 고해상도 인수, 늦은 결과, 실패·로드·dispose를 검증한다. 워커 모형으로 실제 메시지 발행과 준비·실패·세대의 관계를 검증한다. `npm run test:libs`, 앱 빌드, Chrome/WebGPU 브라우저 확인을 실행한다. 브라우저 측정에는 목표 페이지 첫 프리뷰 요청 및 완료, 워커별 렌더 종류, 캐시 재방문의 첫 합성 프레임을 기록한다.

### #2 수정한 계획의 상태 전환 검토

- 상태 SUCCESS, 기준 `429fc0b`, 제품 소스 변경 없음
- 2차 Claude Sonnet 5.5 검토 6건. 외부 호출과 취소 응답까지 포함한 슬롯 알림, 부분 실패로 인한 역할 재배정, 현재 DPI·viewport 범위로 타일 보호 제한, 모든 화면 변경 진입점의 시간 갱신, A→B→A의 동일 키 재수용, 실패 페이지 이후 진행을 수용했다.

- 저해상도 두 방향은 사용자 예시와 같이 페이지 인덱스 단위로 진행한다. 가시 스프레드의 두 장을 모두 보호한다. 현재 화면의 고해상도 워커는 하나를 유지해 전환을 위한 예비 슬롯을 남긴다.
- 기존 Chrome/WebGPU Playwright 13/14. 상세 테스트는 기존 전체 페이지 타일 가정과 대기 방식에 따라 실패했다. 제품 변경 후 실제 viewport의 좌표 범위를 검증한다.

- 두 고해상도 슬롯이 동시에 사용 중인 경우는 제어 가능한 워커 테스트에서 검증했다. 모바일 및 실제 복잡한 대형 PDF의 브라우저 지연은 측정 범위 밖이다.

### 검수 #4

1. 실제 소비 경로는 빌드된 앱과 브라우저 PDFium 워커다. 변경 전후 12페이지 측정과 변경 후 80페이지 업로드, 최종 Playwright가 그 경로를 사용했다.
2. 같은 실패를 그대로 재실행하지 않았다. 과거 타일 테스트의 전체 페이지 가정을 viewport 검증으로 바꿨고, 그 과정에서 발견한 공급자 전환 문제는 DOM 수명 변경으로 해결했다.
3. 제어된 워커 테스트에 더해 앱 진입점, 세 가지 공급자 및 WebGPU 브라우저 합성까지 확인했다.
4. 흰 화면을 줄이는 목표, 200ms·500ms, 네 워커 및 요청 한 건 조건을 유지했다. 브라우저 타일 검증은 viewport 안의 정확한 좌표 집합을 비교한다.
5. 구현을 막는 조건은 없다. 다중 기기 및 복잡한 PDF 성능은 별도 실측 범위다. 판정 CONTINUE, 요청 범위의 이터레이션을 닫는다.
